0005 — WRITING STYLE GUIDE
LEGAiSEE COMMANDCENTER KNOWLEDGE SYSTEM

Version: 1.0
Status: ACTIVE GOVERNANCE STANDARD
Scope: All documentation within /commandcenter/governance/KnowledgeSystem/

1. PURPOSE

This document defines the linguistic, structural, and cognitive style rules for all Knowledge System writing.

Its purpose is to ensure:

consistent interpretability across all system documents
elimination of ambiguity in governance interpretation
stable long-term readability for both humans and system agents
strict alignment between documentation and execution behavior

This is not stylistic preference.

This is enforced system behavior encoding.

2. CORE WRITING PRINCIPLES

All Knowledge System writing MUST adhere to the following principles:

2.1 Clarity Over Density

Every statement must be optimized for immediate comprehension.

No compressed logic chains without explicit expansion
No implied meaning requiring inference beyond one step
2.2 Deterministic Language

All instructions must resolve into a single interpretation.

Required modal verbs:

MUST
MUST NOT
REQUIRED
FORBIDDEN

Avoid:

should
might
could
generally
typically
2.3 System-Centric Perspective

Writing must describe:

system behavior
system constraints
system interactions

NOT:

author intent
narrative explanation
conceptual philosophy (unless explicitly governance-relevant)
2.4 Operational Truth Bias

All statements must reflect operational reality of the system.

If a behavior is not implemented, it MUST NOT be described as active.

3. STRUCTURAL STYLE RULES
3.1 Hierarchical Clarity

All documents must use:

numbered sections (1, 2, 3…)
nested subsections (2.1, 2.2…)
clear separation between rules and explanations
3.2 Section Purity Rule

Each section MUST contain only one type of content:

Definitions section → definitions only
Rules section → rules only
Protocol section → procedural steps only

Mixing categories is forbidden.

3.3 Atomic Paragraph Rule

Each paragraph must contain:

one idea
one constraint
or one system behavior

No multi-concept paragraphs allowed.

4. LANGUAGE TONE SPECIFICATION
4.1 Neutral Technical Tone

Writing must be:

non-emotional
non-persuasive
non-narrative
non-marketing
4.2 No Anthropomorphism

Forbidden constructions:

“the system thinks”
“the system believes”
“the system understands emotionally”

Replace with:

“the system processes”
“the system evaluates”
“the system executes”
4.3 No Conversational Drift

Forbidden:

rhetorical questions
informal transitions (“let’s look at…”)
casual explanation framing

All content must remain declarative.

5. TERMINOLOGY CONTROL
5.1 Fixed Vocabulary Requirement

Core system terms MUST remain consistent:

Kernel Layer
Brain Layer
Engine Layer
Module Layer
Governance Layer
Data Layer
Knowledge System

No synonyms allowed for these terms.

5.2 Precision Naming Rule

All references must be:

exact
capitalized consistently
identical across all documents

Example:

Correct:

Brain Layer

Incorrect:

brain system
cognition layer
reasoning engine layer (unless referring to Engine Layer explicitly)
6. EXPLANATION DEPTH STANDARD
6.1 Three-Layer Explanation Model

When explaining any system behavior:

Layer 1 — WHAT IT IS
Layer 2 — HOW IT OPERATES
Layer 3 — WHAT IT AFFECTS

All three layers must be present when complexity exceeds a single sentence.

6.2 No Hidden Logic

All system behavior must be explicitly stated.

No:

implied workflows
assumed execution paths
implicit dependencies
7. GOVERNANCE LANGUAGE CONSTRAINTS
7.1 Enforcement Markers

All rules MUST use explicit enforcement markers:

MUST
MUST NOT
REQUIRED
FORBIDDEN
7.2 Prohibition of Soft Language

Forbidden phrases:

“it is recommended”
“it is suggested”
“it is preferred”
“best practice”

All governance rules are absolute unless explicitly marked otherwise.

8. CONSISTENCY ENFORCEMENT

All Knowledge System documents MUST:

match this writing style exactly
avoid stylistic drift across versions
maintain identical structural rhythm
preserve terminology consistency across files

Any deviation is considered documentation drift failure.

9. VALIDATION CHECKLIST (MANDATORY)

Before finalizing any Knowledge System document, verify:

 Uses deterministic language (MUST / MUST NOT)
 Contains no ambiguous modal verbs
 Maintains system-centric perspective
 Follows hierarchical structure rules
 Avoids conversational tone
 Uses fixed terminology consistently
 Contains no anthropomorphic language
 Contains no implicit logic

If any item fails → document is invalid.

10. ROLE OF THIS DOCUMENT

This Writing Style Guide functions as:

linguistic governor for all Knowledge System outputs
enforcement layer for documentation consistency
interpretability stabilizer across system evolution
long-term coherence mechanism for system memory integrity

It is a binding constraint, not a guideline.
